# Music Sequencer v4 (The Multi-Track Model) --- Completed on 02/20/2026

## Description: This is the fourth iteration of the Music Sequencer (Formerly known as Chord Orchestrator). This version 4.0 model has completed the shift from a hard-coded script, to a data-driven musical engine. In short, it now allows for the ability to dynamically append new "tracks" onto a given song, with their own respective data. In contrast to the previous model, where even though the MIDI-specific musical data was improved upon in terms of scope, it ended up creating a bottleneck that I noticed after completion, didn't allow for the implementation of new tracks should anyone request it. For functional, organizational, and scalability reasons, I decided to shift the musical data from a hard-coded declaration to an expandable dictionary called 'TRADCK_PROFILES', where should I the developer, find that a given track requires more "musical layers" or instruments running simultaneously to replicate a song, I could then add another "new instrument" as necessary. In terms of practicality, however, I acknowledge that until the AI learning model is further developed to replicate and create its own music, adding new tracks is not a required function for the time being. The implementation of a "Track Profiles" dictionary also serves as a pre-cursor for future SQL integration, as once the Markov Chains are implemented into the program, it will require a frame of reference to take information from. This further increases the scale of the program, as mapped elements such as the chromatic scale 'NOTE_MAP', 'CHORD_MAP', and 'TRACK_PROFILES', in addition to future key-value pairs can all be stored in one place, easy to access, index, and cross-reference. Another key addition to this version is the ability for the user to choose the option for a track to play either "notes" or "chords". This issue was realized early after implementation of the previous model, as the program would still be a "Chord Generator", and not a "Musical Engine" at that point. Now, the user is able to select the specific mode for each MIDI object that they create, giving them the ability to alternate between notes and chords as they see fit. Finally, in its current state, the Music Sequencer does not have the ability to dynamically save MIDI files (Will only save the file as one name, constantly overwriting itself).

## Design Decisions: The '.addProgramChange()' function from 'midiutil' has now been applied to each Track Profile using a loop. This allows each profile to have a completely unique identity, unlike the previous version, where only track 0 had these changes applied to it, and the other tracks, though they existed, were in a default state. In addition, '.addTrackName()' now utilizes a dynamic naming scheme, that takes the designated 'profile["name"]' from its respective dictionary. 'addTrackTempo()' now also has the values for tempo and offset hard-coded, in order to keep this portion of musical data universal across all tracks, thus preventing the loops from redundant actions. 'VALID_TRACK_MODES' has also been implemented as a dictionary to support boolean arguments in the main function, their sole purpose being to create a "hidden state" for the chord prompt, allowing the user to bypass it should the user choose to select a single note for their input. This led to the implementation of 'TRACK_PROFILES["mode"]', which lets the user change between whether a track wants 'mono' or 'poly' inputs (With the former representing single notes and the latter representing chords). Another UX-friendly change was the ability for the user to start their song at a custom offset. Admittedly, a refinement opportunity is present in tha ability to  re-prompt the user once they have selected a custom offset in case they want to choose again. However, for functionality's sake, this will surely be implemented, but only considered in a future iteration. Similarly, this is why the next version will also have the ability to save multiple files, as the learning model will then require the aforementioned function. Lastly, the note variables have also been named to 'octave' the moment they became a dictionary key for a mixture of clarity and consistency across all Track Profiles.

## Other Details: The security checks have now been further enhanced to accommodate with the increased number of required user input. In particular, the check for user_mode now adds a try/except block testing if the user enters a valid offset. If a correct number is entered, the new offset is determined and if no offset is entered and the user just presses Enter, it defaults to 0 and proceeds without considering the if statement. Only invalid entries are flagged, since the offset will fail to convert the input into a float data type. The 'skip_chord_prompt' boolean variable introduces a limiter to the number of options the user has when selecting a "Track Mode" from which to play their notes. The decision was made to reduce the number of redundant information the user sees while deciding whether to input single notes or chords. The new "state" variable now only allows for the implementation of a default value for 'user_chord_type' (In this case, set to "major"), but provides enough security checks that a simple 'if not skip_chord_prompt' will automatically verify the user has correctly chosen the 'poly' option without any prior errors purely by process of elimination.

## Dependencies: sys, midiutil, MIDIFILE
